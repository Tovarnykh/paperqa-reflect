# Сильный PaperQA baseline

**Позднейшая проверка 1 октября:** [сравнение локальных моделей](../results/reports/2026-10-01-local-model-comparison.md).
Gemma QAT рекомендована для дальнейшей настройки по скорости и завершению;
8/8 и 6/8 на двух seed не устанавливают победителя по качеству. Qwen reference-v1
ниже — историческая квалификация: её текущий повтор дошёл до timeout первого
вопроса. Данные сохранены, финальная модель не заморожена.

Статус на 1 октября 2026: рабочий локальный reference прошёл восьмивопросную
dev-квалификацию — 7 правильных ответов, 8 штатных завершений. [Результаты](../results/reports/2026-10-01-strong-baseline.md),
[зафиксированный профиль](../results/baselines/local-reference-v1.json).
Название `high_quality` означает пресет upstream, а не глобально лучшую модель.

## Сравнение и границы

Основной эксперимент остаётся локальным: обычный PaperQA → тот же PaperQA с одним
исследуемым изменением. Модели, корпус, prompts, лимиты и оценщик должны совпадать,
кроме изучаемого фактора. Замену модели или исправление обвязки нельзя выдавать
за эффект нового verifier/controller.

- `configs/baseline-local-dev.json`: сохранённый диагностический кандидат с
  Qwen3 8B и BGE-M3 567M для embeddings. Контекст LLM 16384, выход до 4096 токенов,
  thinking off. Не квалифицирован: частые ошибки native tool calling.
- `configs/baseline-local-qwen35-dev.json`: второй локальный кандидат, Qwen3.5 9B
  во всех трёх LLM-ролях при тех же остальных настройках. Добавлен после повторных
  нарушений tool-call протокола у Qwen3 8B; также не квалифицирован из-за 7/8 fail.
- `configs/baseline-local-qwen35-structured-dev.json`: вариант совместимости
  с JSON-схемой controller-запросов и thinking только у controller. Это выбранный
  рабочий local-reference-v1, явно адаптированный для локального запуска.
- `configs/baseline-upstream-openai-dev.json`: необязательный control с точными
  upstream IDs `gpt-4o-2024-11-20` и `text-embedding-3-small`. Это открытый
  релизный профиль, не современный SOTA и не обязательная облачная зависимость.

Прежние локальные конфигурации сохранены для воспроизведения старого пилота.
PaperQA закреплён на `57e89f7223b0960d5ee5ea048c69e3c47e088572`, `v2026.08.12`;
1 октября GitHub API показывал его последним опубликованным релизом.
Пресет читается из установленного пакета, без подмены пользовательским preset.

## Восстановленные настройки

Стандартные system/RCS/answer prompts, `evidence_k=20`, `answer_max_sources=5`,
чанки 7000 символов, overlap 250, отсутствие ограничения на число шагов.
`answer_max_sources` ограничивает контексты, не обязательно уникальные статьи.
Локальные context/output limits явно заданы в JSON; запуск не неограниченный.

Адаптации: фиксированные 16 TXT-статей, metadata из manifest, без внешнего
получения библиографии и изображений, отдельная индексация перед вопросами,
fresh index на run. Локальный RCS последователен из-за одной GPU; timeout увеличен.
Router retries отключены. Полный diff против upstream сохраняется в
`upstream-deviations.json`. Для локальных embeddings запрещена молчаливая обрезка.
Это не полное воспроизведение PaperQA2 2024 или приватного сервиса FutureHouse.

Локальный профиль дополняет стандартный controller prompt только инструкцией
о формате: вызывать tools и завершать через `complete`; формат финального ответа
не переносить на управляющие сообщения. Это явная адаптация к Ollama: установленный
LiteLLM удаляет `tool_choice=required`, а первый реальный прогон завершился
ошибкой именно из-за обычного текста после `gen_answer`. OpenAI control сохраняет
upstream prompt без дополнения. Эту адаптацию нужно одинаково применять к обеим
сторонам будущего локального сравнения; она не является нашим исследовательским механизмом.

Вариант `json-schema-v1` использует подкласс Settings с обычным Aviary ToolSelector
и адаптером его completion-функции. Все доступные tools, их описания и схемы
аргументов берутся из PaperQA. Модель возвращает один или несколько вызовов;
JSON проверяется и переводится в обычный `ToolRequestMessage`. Код не выбирает
за модель поиск/ответ/остановку, не исправляет её ответ по ключу и не создаёт
автоматическое `complete=true`. Повреждённый/обрезанный JSON остаётся ошибкой.
Для истории tool results сериализуются как помеченные наблюдения. Поэтому
представление controller-контекста отличается от native API и явно фиксируется
в settings/config/source snapshot. В будущем обе стороны сравнения должны
использовать один и тот же транспорт.

На Ollama 0.30.10 диагностический replay с `think=false` проигнорировал format.
Повтор с thinking controller вернул валидный вызов `gen_answer`. Сходная причина
видна в [коде именно этой версии](https://github.com/ollama/ollama/blob/v0.30.10/server/routes.go)
и [исправлении upstream](https://github.com/ollama/ollama/pull/15901).
`agent_reasoning_effort=low` здесь означает **Ollama think=true**, не градацию
силы reasoning Qwen. Прочие роли сохраняют `think=false`. Отдельное обновление
Ollama не выполнялось. Replay — проверка транспорта, не новый правильный ответ
и не независимая оценка качества. Время replay пересекалось с native-серией.

`nomic-embed-text` не оставлен в новом профиле: сервер ограничивал его контекст
2048 токенами, а проверка всех 174 upstream-чанков с `truncate=false` вернула
HTTP 400. BGE-M3 (8192 токена, 1024 измерения) взят для устранения этого ограничения,
не на основании измеренного превосходства на LitQA. Используем его dense embeddings;
другие режимы BGE-M3 не добавлялись. Новый тег и digest фиксируются каждым run.

Для установленного Ollama также нужен `embedding_batch_tokens=8192`: его
физический batch по умолчанию 2048 отклонял целые фрагменты длиной 2100–2400
токенов даже при контексте 8192. Это настройка вычисления embedding, не размер
чанка и не число одновременно оцениваемых вопросов. После изменения проверка
всех 11 чанков первой статьи прошла без обрезания; полная индексация проверяет
остальные документы перед переходом к вопросам.

## Запуск

Из корня репозитория:

```powershell
uv sync --frozen
powershell -ExecutionPolicy Bypass -File scripts/start-ollama.ps1
$env:OLLAMA_HOST = '127.0.0.1:11435'
ollama pull bge-m3:567m
ollama pull qwen3.5:9b
uv run --frozen pqa-reflect plan --config configs/baseline-local-qwen35-structured-dev.json
uv run --frozen pqa-reflect doctor --config configs/baseline-local-qwen35-structured-dev.json
uv run --frozen pqa-reflect run --config configs/baseline-local-qwen35-structured-dev.json --limit 1
uv run --frozen pqa-reflect run --config configs/baseline-local-qwen35-structured-dev.json --limit 8
```

`plan` проверяет корпус и реальный API установленного PaperQA без inference,
сохраняет settings/diff в `results/plans/<config>/`. `doctor` дополнительно
проверяет Ollama/модели либо наличие переменной с ключом. Они не доказывают
качество ответа или успешность платного запроса. Перенос на UiA возможен через
loopback SSH-туннель; серверные доступ и VRAM ещё надо проверить.

Для optional OpenAI control ключ нужен в переменной процесса `OPENAI_API_KEY`.
`.env` автоматически не загружается. Ключ не сохраняется в JSON, Git или чате.
Команды те же, с `baseline-upstream-openai-dev.json`. Сначала один dev-вопрос,
после проверки результата и расходов — серия.

## Данные результата

Config/settings/diff, версии/hashes, снимок исходников, digests моделей,
индексация, действия агента, исходные evidence, ответы и ошибки сохраняются.
`requests.jsonl` наблюдает LiteLLM-вызовы, включая controller и embeddings,
без ключей и содержимого запросов. `usage.json` содержит наблюдаемые оценки
стоимости; неизвестная стоимость не считается нулевой. Локальная нулевая
API-стоимость не включает электричество и оборудование.
Счётчики токенов берутся из ответов провайдера; для двухфазного structured
generation Ollama они не гарантируют отдельный полный учёт thinking-токенов.
По ним нельзя объявлять доказанную экономию вычислений.

У OpenAI control порог $3 проверяется **между вопросами**, включая индексацию.
При неизвестной стоимости следующий вопрос не запускается. Уже выполняющийся
вопрос может превысить порог: это не жёсткий лимит оплаты. Общий бюджет проекта
$100 учитывается отдельно у провайдера; программа не видит другие запуски/judge.

Отдельные показатели: правильная буква, правильный завершённый ответ, coverage,
отказы, ошибки контроллера, источники, токены, времена индексации и вопросов.
Наличие нужного DOI не доказывает поддержку утверждения. Claim-level judge
пока не запускался. Восемь dev и восемь reserved — лишь небольшой пилот.

## Условия фиксации baseline

1. Индексируются все документы без незаметной обрезки embedding-входа.
2. Полная dev-серия сохраняет все попытки. Разобраны ошибки транспорта,
   tool calls, context/output limits и объяснений; их не скрывают средней accuracy.
3. При смене модели сначала измеряется обычный PaperQA на этой же модели.
   Не подгоняем prompts под восемь известных вопросов.
4. Профиль и hashes фиксируются до holdout; резерв не используют для подбора.
   Для серьёзного вывода расширяем оценочный набор.
5. Baseline и механизм сравниваются попарно на общих вопросах. Ни готовый config,
   ни успешный одиночный ответ не означают завершённую научную оценку.

Современный API не всегда допускает простую замену имени: на 1 октября
документация GPT-6.1 Sol требует Responses API для tool calls, а закреплённый
ToolSelector использует Chat Completions через Router. Эта интеграция не выполнена;
модель не включали как якобы проверенный baseline и не понижали reasoning ради
совместимости. Возможная современная API-проверка остаётся отдельной работой.
