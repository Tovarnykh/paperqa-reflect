# Первый эксперимент: локальная проверка поддержки утверждений

**Позднее 3 октября:** observer A реализован и выполнена первая серия; [результаты](../results/reports/2026-10-03-verifier-first-run.md). Ниже сохранён исходный план. Уточнение context32768 до первого вызова описано в [руководстве](local-verifier.md); bounded revision B ещё не реализован.

Дата: 3 октября 2026. Версия: **план перед реализацией**, подготовленный по поручению
пользователя. Наблюдатель, исправление ответа и новые прогоны ещё не реализованы.
Baseline уже выбран; повторный поиск «лучшей модели» не входит в этот этап.

## 1. Вопрос и проверяемая гипотеза

Может ли проверка отдельных утверждений по **оригинальным процитированным фрагментам**
с одним последующим исправлением повысить обоснованность ответов PaperQA, сохранив
правильность и полноту ответа при приемлемой измеренной дополнительной стоимости?

Разделяем два эксперимента:

- **A, ближайший:** verifier как наблюдатель классифицирует заранее выделенные
  утверждения. Проверяем, можно ли доверять его замечаниям. Ответ PaperQA неизменен.
- **B, после A:** замечания используются для одного исправления. Проверяем уже
  качество исправленного ответа и сравниваем с простым повторным просмотром.

Хорошая классификация в A не доказывает улучшения PaperQA в B. Обнаружение ошибки
не требует автоматически искать новые статьи: иногда достаточно исправить число,
формулировку или ссылку на уже имеющийся фрагмент.

## 4. Что получает и возвращает verifier

Вход: одно самостоятельное утверждение и список **полных исходных процитированных
фрагментов**. Точное извлечение из `review.json -> contexts[].text.text`.
RCS-резюме, эталонная буква, правильный ответ, наши labels/rationales и подсказанные
опорные строки в модель не передаются. Исходный текст — данные, а не инструкции.

Сначала используем вручную выделенные утверждения: автоматическое разделение
ответа — отдельный возможный источник ошибки, его нельзя смешивать с качеством
проверки. Каждое утверждение связано с исходной фразой и её позицией.
Не теряем «примерно», «в данном опыте», «предположительно», «не указано».

Выход одной проверки:

```json
{
  "case_id": "cv-001",
  "label": "supported",
  "evidence": [{"passage_id": "p-...", "quote": "exact source substring"}],
  "explanation": "Brief source-grounded reason"
}
```

Это **пример интерфейса**, а не полученный ответ модели. Допустимые метки:

| Метка | Правило |
|---|---|
| supported | Предоставленные фрагменты подтверждают всё утверждение, включая субъект, число и ограничения |
| contradicted | Предоставленный текст содержит несовместимые данные при том же субъекте и условиях |
| insufficient | Поддержки недостаточно; это не означает, что утверждение ложно во всём мире или во всей статье |

Отдельное транспортное состояние `not_checked` используется для timeout,
невалидного JSON, недопустимого ID, выдуманной цитаты или превышения контекста.
Оно не является четвёртым смысловым label и не превращается в insufficient.
Проверяем точное присутствие возвращённой цитаты в оригинале детерминированно.
Для supported/contradicted требуем опорный текст. Для insufficient разрешён пустой
evidence: отсутствие сведений обычно нельзя доказать одной цитатой.

Совместная поддержка несколькими источниками допустима: сначала оцениваем их
совокупность. Частично полезный фрагмент нельзя объявлять лишним лишь потому, что
он один не доказывает весь вывод. Противоречащие друг другу источники сохраняем
как конфликт: insufficient с объяснением конфликта, без произвольного выбора истины.
Невосстановленная ссылка/неясная привязка фиксируется как проблема входа до inference.
Фактическое утверждение без ссылки учитывается в полноте цитирования; оно не исчезает
из будущей оценки. Разрешается только явно описанное наследование ближайшей ссылки,
не автоматическая подстановка любой подходящей статьи из всех найденных.

## 5. Первая локальная реализация: подготовленная спецификация

Технический старт — **тот же уже установленный Qwen3.8 27B**, в отдельной роли
verifier. Это инженерный выбор для первого прототипа, не доказательство, что он
лучший оценщик. Ошибки с генератором могут коррелировать, поэтому он не выставляет
итоговую научную оценку собственному улучшению.

План начального профиля: Ollama 0.35.0/11436 на UiA, одна последовательная проверка
за раз, context 16384, max output 1024, temperature 0, seed 42, thinking off,
без presence penalty, timeout 600 s. Prompt, фактический model digest и полный
профиль фиксируются перед первым вызовом. Это ещё **не проверенная конфигурация**;
temperature 0 не гарантирует абсолютную воспроизводимость. Повтор всех случаев
с seed 43 показывает вариативность, а не удваивает число независимых примеров.

Не делать молчаливого усечения: предварительно оценивать размер входа, сохранять
фактические token counters и флаги truncation. Слишком большой случай получает
`not_checked/context_overflow`. Оконная обработка или отбор фрагментов потребуют
отдельной версии протокола. Дедупликация одинакового исходного текста разрешена
с сохранением всех исходных ID. Ограничение числа citations не вводится скрыто.

Сначала сохранить raw response, разобранный verdict, время, tokens и ошибку каждого
запроса. Повтор не должен заменять неудачу «лучшей попыткой». Никаких действий
controller, нового поиска или перезаписи сохранённого ответа в A.

## 6. Оценка наблюдателя

На естественных и искусственных примерах — **отдельные таблицы**:

- матрица ошибок по трём классам, precision/recall/F1 каждого класса, macro-F1;
- доля supported, ошибочно помеченных contradicted/insufficient (ложная тревога);
- точность флагов: действительно проблемные / все помеченные проблемными;
- полнота флагов: найденные проблемные / все проблемные по независимой разметке;
- доля `not_checked`, неверных цитат и невалидных ответов;
- wall time, input/output tokens, число вызовов, загрузка модели отдельно.

Знаменатели нулевой величины дают NA, не 0 или 100%. Основные классификационные
метрики приводятся на checked случаях вместе с покрытием; дополнительно считаем
консервативную accuracy по всем запланированным случаям, где not_checked — ошибка.
Не делать статистических выводов по двум противоречиям. В итоговом paired-анализе
группировать по вопросу/статье и усреднять повторы внутри группы, не выдавать
десятки связанных claims за независимые наблюдения.

Человек проверяет утверждения по полным фрагментам, по возможности не видя имя
системы, её verdict и assistant labels. Разногласия сохраняются до adjudication.
Можно начать с Viktor как единственного независимого от verifier проверяющего;
в отчёте указать число проверяющих и отсутствие измерения межэкспертного согласия.
Помощник уже видел ответы и ключи: его текущая разметка — dev draft, не human gold.
Отдельный hosted judge остаётся необязательным дополнительным оценщиком после
проверки его решений человеком, не заменой этой процедуры.

## 7. Условия перехода

**К созданию наблюдателя — готовы**, когда пакет воспроизводится, ссылки/offsets
и исходные hashes валидны, вход отделён от labels, правила и фиксированный baseline
записаны. Независимая разметка не нужна, чтобы написать и отладить этот интерфейс.

**К пробному исправлению B** переходим после реальных результатов A и проверки
labels человеком. Предварительный инженерный gate для данного малого dev-пакета:

1. Все случаи имеют сохранённый исход; нет молчаливого усечения или принятого
   невалидного evidence. Технически непроверенные случаи сначала исправляются.
2. Среди естественных случаев правильно обнаружено хотя бы одно противоречие
   и один случай недостаточной поддержки; верных флагов больше ложных.
3. Verifier принимает оба искусственных supported-контроля (исправленную ссылку
   и осторожное утверждение о неупоминании), а не только отвергает всё подряд.
4. Разобраны все ложные тревоги и пропущенные ошибки; измерены дополнительные
   затраты. Прохождение этого gate позволяет **пилот B**, но не вывод о надёжности.

Это выбранные здесь инженерные критерии, не стандарт из статьи и не статистическое
доказательство. Если gate не пройден, сохраняем отрицательный результат, меняем
prompt/профиль на dev и версионируем; резерв не открываем ради подбора.

## 8. Сравнение исправления и контроль дополнительного вычисления

Будущий B берёт один и тот же сохранённый финальный ответ и evidence для трёх веток:

| Вариант | Действие |
|---|---|
| B0 | Исходный зафиксированный PaperQA |
| B1 | Обычный пересмотр полного ответа по тем же исходным фрагментам, затем одно исправление |
| B2 | Проверка отдельных claims, затем одно исправление по структурированным замечаниям |

B1 и B2 видят одинаковый доступный исходный evidence и исходный ответ. Это отделяет
проверку claims от эффекта доступа к несжатому тексту. Одинаковая модель исправления,
лимит итогового ответа и запрет нового поиска. На bounded revision можно заменить
неверную ссылку другой **уже найденной**, ослабить формулировку или исправить факт.
Исходный ответ всегда сохраняется, при техническом сбое остаётся результат B0.

Начальный B1 контролирует пользу обычного review, но не является точным контролем
compute: проверка многих claims делает больше вызовов. Сравниваем реальные token/time
затраты; если B2 выигрывает при большем бюджете, добавляем budget-matched B1 до
утверждений о выгоде именно архитектуры. Политика лимитов фиксируется после замеров
A на dev и до нового validation/test. Точные лимиты B ещё не замерены и не заморожены.

Основной outcome B: доля фактических утверждений, полностью поддержанных своими
цитатами (все фактические claims ответа, включая claims без citations, в знаменателе).
Отдельно показываем contradicted/insufficient, долю ответов без ошибок и полезность
отдельных citations с учётом совместной поддержки. Это наша адаптированная метрика,
не точная реплика ALCE/FActScore.

Ограничители: MCQ accuracy со статусом завершения, abstention/coverage, число
фактических утверждений, сохранение заранее размеченных необходимых частей ответа,
новые ошибки после исправления. Удаление всего объяснения не считается улучшением.
Пустой ответ имеет неопределённую claim precision и нулевую полноту, не 100%.
Для итогового улучшения требуются положительное paired изменение поддержки,
отсутствие наблюдаемого ухудшения accuracy/обязательной полноты и отчёт о затратах;
это не доказательство статистической эквивалентности качества на малой выборке.

## 9. Расширение данных и закрытая оценка

Текущие 26 случаев используются только для реализации и отладки. После A нужен
естественный набор **всех** claims выбранных ответов, без отбора только интересных
ошибок. Предлагаемый следующий объём: 24 новых вопроса по прежнему детерминированному
OA/text-only правилу, 12 development и 12 locked evaluation. Имеющиеся 8 reserve
остаётся резервом; вместе это даст 20 evaluation-вопросов, всё ещё малый пилот.
Это план объёма, не уже созданный split и не расчёт статистической мощности.

До новых запусков фиксируем roster, уникальные question/article IDs, основания
исключения, corpus hashes и размеры split. Исключаем все уже использованные dev
и резервные IDs/целевые статьи; технические исключения записываем до просмотра
ответов. Корпус расширяется симметрично для всех вариантов. Сначала измеряем
неизменённый baseline на новом dev, размечаем все claims и только потом сравниваем
изменение. Разделение по claims одного ответа между train/dev/test запрещено.

Окончательный размер и лимиты B должны быть зафиксированы до открытия locked
evaluation, с учётом стоимости A и доступных ресурсов. Если достаточно только
нынешнего резерва, честно ограничиваем выводы пилотом. Любая настройка по резерву
превращает его в dev; текущей подготовкой резерв не читался и не запускался.

## 10. Основания и границы новизны

Проверка claims по evidence уже изучалась; «добавили verifier» само по себе не новая
идея. Возможный вклад курса — воспроизводимое локальное применение к выбранной
PaperQA, измерение ошибок RCS/привязки citations и эффекта ограниченного исправления.
До финального заявления о новизне нужен более широкий обзор близких работ.

- [FActScore, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.741/), §3:
  полезен принцип отдельных проверяемых фактов и поддержки источником. Мы не
  переносим его численные результаты или биографический benchmark на PaperQA.
- [ALCE, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.398/), §3 и Appendix F:
  различает корректность ответа и качество цитирования; несколько citations могут
  совместно подтверждать утверждение. Наша трёхклассовая рубрика — адаптация.
- [RAGTruth, ACL 2024](https://aclanthology.org/2024.acl-long.585/): мотивирует
  разбор неподдержанных/противоречащих контексту фрагментов и человеческую разметку.
  Dataset и обученные модели этой работы сейчас не интегрируются.

Сохранённые идеи Jev пересмотрены: дословные опорные фрагменты, отдельная оценка
verifier и наблюдение до обратной связи подходят этому плану. Jev API, маршрутизация
моделей и новый controller не нужны для A и не реализованы. Возврат к ним возможен
по результатам локального механизма, а не как обязательная часть первого эксперимента.

## 11. Ближайшая реализация после этой подготовки

Сделать отдельный offline CLI для `cases.jsonl + passages.jsonl`, строгий парсер
verdict/цитат, журнал всех попыток и отчёт сравнения с разметкой, подключить
локальный Ollama и выполнить A. Не менять PaperQA и не вызывать существующий
`run` для этого шага. Затем объяснить пользователю конкретные ошибки verifier.
Автоматическое извлечение claims из полного ответа и bounded revision идут позже.
