# Протокол первого сравнения: litqa-pilot-v1

Зафиксирован 19 сентября 2026 до запуска моделей на LitQA-пилоте. Это рабочая
основа этапа 4; объём итогового исследования и финальная гипотеза остаются открытыми.

Дополнение после диагностической попытки: запуск TXT-корпуса требует UTF-8.
Upstream reader использует системную кодировку по умолчанию; в Windows некоторые
греческие символы искажались без исключения. CLI теперь автоматически запускает
Python с `-X utf8`, а encoding сохраняется в provenance. Попытка
`20260919T155017Z-73ddc2` остановлена после двух завершённых вопросов и не считается
сопоставимым baseline. Новый полный запуск использует тот же корпус, вопросы,
модели и научные правила оценки. Изменён способ чтения текста, не модель.

## Задача и baseline

Проверяем, как выбор локальной модели влияет на качество и стоимость выполнения
вопросов по научным статьям в одной конфигурации PaperQA. Начальная точка —
неизменённая библиотека PaperQA из закреплённого коммита, Qwen3 8B во всех трёх
LLM-ролях, nomic-embed-text для embeddings. Конфигурация:
`configs/litqa-dev-qwen3-8b.json`. Собственного verifier или правила остановки нет.
Уточнённый system prompt ToolSelector унаследован от smoke-v2 и одинаков для
сравниваемых конфигураций; это отличие от настроек upstream по умолчанию.

Это **локальный baseline на фиксированном корпусе**, а не воспроизведение
опубликованного PaperQA2 с интернет-поиском, исходными моделями и полным LitQA2.
Здесь не проверяются автоматически H1–H3 исходного proposal. Для этих гипотез
понадобятся дополнительные контролируемые эксперименты.

## Данные и границы вывода

- Источник вопросов: [FutureHouse LAB-Bench, LitQA2](https://huggingface.co/datasets/futurehouse/lab-bench/tree/5c77cec648430f30611808808861eb86f81d5eaa/LitQA2).
  В закреплённом файле 199 вопросов. Upstream `train` — имя опубликованного split;
  мы не обучаем на нём модели. Это не частный тест авторов.
- Наши **8 dev + 8 holdout** выбраны до просмотра результатов модели. Вопросы
  отсортированы по SHA-256(`ikt464-pilot-v1:` + ID); взяты первые 16 с доступным
  OA JATS-текстом Europe PMC, уникальными источниками и корректными вариантами.
  Принятые вопросы попеременно распределены между dev и holdout. Полный журнал
  рассмотренных 30 кандидатов, исключений и временных HTTP-ошибок сохранён в
  `data/manifests/litqa-selection.json`. Наличие эталонного фрагмента в тексте
  проверяется диагностически, но не использовалось для отбора.
- В dev и holdout нет общих вопросных ID и целевых DOI/статей. Оба работают
  с одним замороженным корпусом из **16 статей**: для вопроса прочие статьи
  выступают отвлекающими. Тексты резервных статей присутствуют в общем корпусе;
  резервируются вопросы и оценка, а не сами документы.
- Источники: полные основные тексты из [Europe PMC REST API](https://www.ebi.ac.uk/europepmc/webservices/rest/).
  Детерминированно сохраняются заголовок, abstract, body, подписи к рисункам
  и текст таблиц. Списки литературы, внешние supplementary files и изображения
  не включены. Это **text-only режим**; ссылки показывают позиции текстовых
  фрагментов, а не страницы исходного PDF.
  В upstream `chunk_chars=3000` для TXT преобразуется в размер по токенам
  с перекрытием: фактическая длина фрагмента может превышать 3000 символов.
- Лицензия вопросов — CC-BY-SA-4.0; происхождение, canary, исходные формулировки,
  эталоны и перемешивание вариантов сохранены. Лицензия каждой статьи записана
  отдельно в manifest. Сырые XML и извлечённые тексты в Git не включаются.
- По всем восьми dev-вопросам опорный ответ есть в извлечённом тексте: у семи
  совпадает нормализованный фрагмент; у восьмого различается запись символов
  и степеней, но предложение о flocculation присутствует. Это проверка
  доступности источника, не результат агента и не экспертная биологическая оценка.
- Малый размер, доступность OA-текстов и биомедицинский домен ограничивают
  обобщение. Восемь holdout-вопросов дают только предварительную независимую
  проверку; для убедительных итоговых выводов желательно заранее расширить резерв.
  Публичность набора не исключает попадания данных в предобучение выбранных моделей.

## Что доступно агенту

Только вопрос, варианты и индекс папки `data/corpus/litqa-pilot`. Правильная буква,
эталонный фрагмент и целевой DOI хранятся вне корпуса; в prompt проходят только
поля question/options. Индекс не видит wiki, вопросы, gold или предыдущие ответы.
Состав и SHA-256 корпуса проверяются перед каждым запуском. Варианты перемешаны
один раз независимо для каждого ID и одинаковы для всех моделей. При нехватке
доказательств агент может явно ответить `ABSTAIN`.

## Метрики и ошибки

1. **Accuracy:** успешно завершённые ответы с правильной явной буквой / все
   запланированные вопросы завершённой серии. Неверный ответ, timeout, ошибка,
   отсутствие понятной буквы и отказ не становятся правильным результатом.
2. **Coverage:** успешно завершённые ответы с допустимой буквой без отказа / все
   вопросы. **Precision:** правильные / такие отвеченные вопросы; при отсутствии
   ответов — неопределена. Отдельно сохраняются технические статусы, ошибки
   формата, совпадение буквы до проверки статуса и отказы. Категории ошибок могут
   пересекаться. Прерванная серия не сравнивается как полная.
3. **Источники:** присутствует ли целевой DOI среди evidence и среди использованных
   ссылок. Это поиск нужной статьи, а не доказательство поддержки утверждений.
4. **Ресурсы:** время построения свежего индекса отдельно; wall time каждого
   вопроса, вызовы инструментов и учтённые PaperQA LLM-токены. Время вопроса включает
   переключение/загрузку моделей. Embedding-токены могут не входить в счётчик
   PaperQA. Снимки GPU/VRAM в начале и после вопроса не являются пиковым потреблением.
   API-расход на агент в этой локальной конфигурации — $0; электричество и стоимость
   оборудования не измерены. Отдельный бюджет hosted judge ещё не тратится.

`tool_calls` считает инструменты, выбранные агентом, а не все LLM-запросы.
После исчерпания 8 шагов upstream может выполнить дополнительный fallback
`gen_answer`, включая получение evidence. Он входит во время вопроса и доступные
счётчики PaperQA, но не является девятым выбранным агентом шагом. Поэтому статус
`truncated` и журнал PaperQA сохраняются даже при появлении финального текста.

Букву извлекает строгий детерминированный parser строки `Final answer: X`,
допускающий Markdown bold и известные Context ID после ответа. Отдельная LLM
для угадывания выбранного варианта не используется. Поэтому ошибки формата
могут снижать наш результат иначе, чем в опубликованных оценочных pipelines.

Сохраняются все попытки, включая неудачные. Нельзя повторять только ошибки и
затем выдавать лучшие ответы за один запуск. Исправление harness требует новой
версии и повторения сопоставимого baseline. Отчёт о неполном запуске содержит
число завершённых и запланированных вопросов, а не итоговую accuracy.

## Ручная проверка evidence

После каждого вопроса создаётся `review.json`: ответ, эталон, raw passages,
RCS-резюме и Context ID. Для каждого фактического утверждения в выбранной
проверяемой выборке отмечаем: supported / contradicted / insufficient / not-checked.
Проверяем исходный фрагмент, не только резюме. Отдельно отмечаем правильность
центрального ответа, опущенные существенные детали и лишние утверждения.
Автоматическое совпадение буквы эту проверку не заменяет. Наш ручной разбор
ассистентом обозначается как assistant review, а не независимая экспертная оценка.

Для будущей массовой оценки сильной моделью сначала провести маленький пилот
рубрики; давать ей исходные доказательства и анонимизированные ответы. Проверить
порядок A/B и несколько её решений вручную. Это будущая работа: judge сейчас
не выбран и не запущен; будущий verifier не должен быть единственным судьёй себя.

## Правила этапа 4

Dev можно разбирать и использовать для подбора моделей. Holdout запускается
только после фиксации сравниваемых конфигураций; CLI требует `--allow-holdout`.
Если по его результатам меняются настройки, он становится dev и нужен новый резерв.
Не выбирать кандидатов по holdout-ответам. Не менять корпус/чанки одновременно
с изучением эффекта замены модели: каждое такое изменение — отдельный эксперимент.

Сначала заменить одну роль или явно объявить замену всего LLM-стека; прочие
настройки и ограничения сохранить. Для скорости использовать ту же машину,
питание от сети и одинаковую политику загрузки моделей; после первичного отбора
повторить полные серии с чередованием порядка конфигураций. Текущий единичный
прогон показывает практическое время выполнения, но не надёжный эффект ускорения.
Стандартный сервер сейчас допускает одну загруженную модель; warmness не
контролируется полностью и отмечается в provenance. Это возможный объект
будущей оптимизации, а не скрытая настройка уже выполненного baseline.

Переход к этапу 4 означает готовность измерительного стенда и первый измеренный
baseline. Он не требует высокой accuracy: диагностированный неуспешный baseline
тоже задаёт конкретную задачу для улучшения.
