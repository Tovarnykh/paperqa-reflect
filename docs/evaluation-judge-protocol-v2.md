# Оценка PaperQA и локального verifier: внешний LLM judge

**Текущий результат 3 октября:** [ограниченная правка extraction v2 завершена](../results/reports/2026-10-03-measurement-repair-v2.md). 20/20 новых извлечений (включая шесть реальных ответов) получили faithful/complete; проверка оценщика 15/16, спорная формулировка сохранена как ограничение. Используем v2 как рабочую версию и возвращаемся к B0/B1/B2 dev experiment, без нового цикла полировки. Для следующих запусков bounded revision явно указывать `--extraction-version v2` (legacy default v1). API ledger $1,201638 / 177 calls. Более ранние checkpoints ниже — история.

**Статус реализации позднее 3 октября:** [внешний evaluator](external-judge.md) для этапа A готов и протестирован. 26-case offline plan сохранён; реальный API pilot ещё не запускался из-за отсутствующего ключа. Bounded revision и pairwise evaluation остаются планом.

Дата: 3 октября 2026. Статус: пересмотренный рабочий план, **ещё не исполненный
judge pipeline**. Пользователь подтвердил ранее обсуждённый подход: использовать
сильную модель для оценки, не поручать студенту предметную разметку.
Этот документ заменяет обязательную ручную проверку в §§6–7
[протокола v1](claim-verifier-protocol-v1.md). Остальные настройки локального
наблюдателя и зафиксированный baseline сохраняются. Численные лимиты пилота и
проверки устойчивости ниже — предложения помощника, а не требования преподавателя.

## 1. Что уже есть и что исправлено в плане

  [manifest](../results/baselines/uia-local-reference-v1.json).
- Наблюдатель уже выполнил 26 случаев: 20/20 natural и 5/6 controlled совпадений
  с черновой разметкой помощника. Это диагностическое agreement, не проверенная
  точность. [Первый запуск](../results/reports/2026-10-03-verifier-first-run.md).
- Облачной оценки и исправления ответов ещё не было. Старый пакет, annotations,
  predictions и его hashes сохраняются без изменений.
- Ручная разметка Viktor больше не является условием следующего этапа.
  Форма остаётся необязательным историческим инструментом.

## 2. Разные роли

| Роль | Назначение | Может влиять на ответ агента? |
|---|---|---|
| PaperQA baseline | Даёт исходный ответ | Да |
| Локальный verifier | Проверяет claims; позднее даёт замечания для одного исправления | Да, только в экспериментальной ветке |
| Внешний judge | Измеряет качество сохранённых ответов и решений verifier | Нет, в зафиксированном итоговом эксперименте |
| Помощник в этом чате | Разрабатывает протокол, анализирует dev-ошибки, объясняет результат | Только на этапе разработки |

Внешний judge — отдельный вызов сильной модели без истории этого чата.
Планируем использовать имеющийся OpenAI API-доступ; конкретный model ID/snapshot,
настройки и действующая цена фиксируются перед пилотом. Наличие мощной модели
не доказывает её надёжность на нашей рубрике. Не возобновляем подбор baseline.
Разделение ролей снижает прямую самооценку, но не гарантирует независимости ошибок.

## 3. Три вида измерения

**Проверки программой.** Правильная буква по ключу LitQA, успешное завершение,
отказ/покрытие, существование source IDs, точное присутствие цитат, время, tokens,
вызовы и стоимость. Проверка подстроки не доказывает смысловую поддержку.

**Основная содержательная оценка.** Внешний judge проверяет каждое фактическое
утверждение по его исходным cited passages: supported / contradicted /
insufficient. Сохраняет дословное основание и краткое объяснение. Неупоминание
не равно противоречию. Учитываются условия, числа и совместная поддержка
несколькими источниками. Конфликт источников не разрешается произвольным выбором.

**Вспомогательное сравнение полных ответов.** Judge отдельно сравнивает анонимные
ответы по обоснованности, правильности вывода относительно доступного эталона,
полноте ответа на вопрос и существенным пропускам. Возможны A / B / tie /
cannot_assess. Это не один непрозрачный балл «качества 1–10».
Стиль, длина и число ссылок сами по себе не означают лучшего результата.

## 4. Два режима входа, без утечки оценок

**A: проверка самого verifier.** На первом dev-пилоте judge получает существующие
cases.jsonl + passages.jsonl, случайный порядок и нейтральные IDs. Не получает
assistant labels, verifier predictions/explanations, происхождение natural/control,
эталонную букву или имя системы. Все 26 случаев проходят одну процедуру; выводы
natural/control разделяются уже в отчёте. Новые verdicts хранятся отдельным файлом,
не заменяют старые labels. Получаем «согласие с внешним judge», не human gold.
Для такого файла не ставить флаг independently_adjudicated:true.

**B: оценка конечного ответа.** Сохраняются вопрос, полный анонимный ответ,
восстановленная привязка citations и полный исходный evidence. Выделение claims
выполняется отдельной одинаковой процедурой для всех веток; не берём только
утверждения, которые заметил локальный verifier. Нужны исходные answer spans,
сохранение оговорок, учёт всех фактических предложений и явный список фраз,
исключённых как нефактические. Автоматическое выделение claims пока не реализовано;
его пропуски и неудачные разбиения — отдельное ограничение измерения.

Поддержка citation оценивается именно по источникам, привязанным к claim.
Нельзя «спасти» неправильную ссылку подходящим текстом из общего пула. Утверждения
без citations входят в знаменатель и помечаются insufficient/no_citation.
Совместная поддержка нескольких привязанных passages допустима.

Для общей правильности/полноты используется одинаковый для сравниваемых ответов
пул исходных фрагментов и доступный benchmark reference, в отдельном задании judge.
Эталонная буква не заменяет эталонного объяснения. Полнота означает ответ на вопрос
и сохранение нужных условий/обоснования, а не воспроизведение всей науки по теме.
Reference/ключи не передаются генератору, verifier или этапу проверки citations.

Участники не получают judge rationale как подсказку при итоговом исправлении.
На dev результаты допускается использовать для отладки с новой версией; locked
evaluation после настройки превращать обратно в скрытый тест нельзя.
Тексты документов/ответов — данные, не инструкции. Ошибки, переполнение контекста,
выдуманные evidence и усечение учитываются отдельно как not_checked.

## 5. Как проверить оценщик без обязательной разметки студентом

1. Первые 26 dev-кейсов проверяют транспорт, рубрику и характер расхождений.
   Помощник разбирает основания с источниками; спорные случаи сохраняются,
   не переписываются в удобный «эталон». Пример cv-024 особенно важен для различия
   contradicted/insufficient. Эти случаи уже видели при разработке.
2. Для парного сравнения каждый выбранный pair оценивается в двух отдельных
   вызовах A/B и B/A с одинаковой инструкцией. Переводим позиции обратно в IDs.
   Смену победителя или winner/tie несогласие отмечаем order_unstable,
   не превращаем в устойчивую победу. Перестановка не устраняет все ошибки judge.
3. Проверка устойчивости: фиксированная случайная 20% выборка по question IDs
   плюс все нестабильные/спорные случаи — второй сильный judge при доступном
   бюджете. Модель другого семейства предпочтительна; другой seed той же модели
   измеряет повторяемость, а не межмодельную независимость. На dev A дополнительно
   смотреть все расхождения с local verifier. Selection и случайная часть
   фиксируются до просмотра verdicts. Не менять основной score по большинству
   голосов: показывать чувствительность вывода к judge отдельно.
4. Дополнительная дешёвая проверка при пригодности: небольшая фиксированная
   подвыборка уже размеченных научных claims, например SciFact. Это отдельный
   calibration set: сначала проверить лицензию, label mapping и evidence scope.
   Не переносить corpus-level «нет доказательств» на произвольный passage.
   Готовая экспертная разметка полезнее требования новой разметки от Viktor.
   Такой набор пока не выбран/не скачан; его включение не блокирует прототип.

Второй judge и SciFact — проверки устойчивости, не новый обязательный большой
исследовательский трек. Если доступны только один judge и ключи LitQA, сравнение
возможно, но вывод прямо ограничивается этим оценщиком. Межмодельное согласие,
успех на публичном наборе и уверенный тон не доказывают экспертную истинность;
учитываем общий bias, domain shift и возможное знакомство модели с benchmark.
Неразрешённые случаи показываем отдельно и оцениваем, меняют ли они вывод.

## 6. Что сравниваем и как читаем результат

Сохраняем B0/B1/B2 из v1:

- B0: зафиксированный PaperQA;
- B1: обычный пересмотр ответа по тем же исходным passages и одно исправление;
- B2: локальная проверка claims и одно исправление по замечаниям.

B1 и B2 получают одинаковые исходные ответы и доступ к evidence, одну модель
исправления, общий лимит ответа, без нового retrieval. Это ещё не реализовано.
Измеряем добавленные tokens/time; при большем compute B2 не приписываем выигрыш
одной архитектуре без дополнительного сравнения при сопоставимом бюджете.

Основной показатель: для каждого ответа доля factual claims, полностью
поддержанных своими citations по внешнему judge. В знаменателе также claims
без citations и технически непроверенные claims; последние дополнительно
показываются отдельно. На уровне отчёта: среднее по seeds внутри вопроса, затем
среднее по вопросам. Пустой/неудачный ответ получает 0 для агрегата, а не 100%;
его статус, отказ и отсутствие claims показываются отдельно. Для unresolved
judge cases приводим нижнюю/верхнюю границы, не скрываем их удалением из выборки.

Обязательные соседние показатели: key-match accuracy со статусом завершения,
coverage/abstention, число противоречий, доля ответов без неподдержанных claims,
полнота по заданию, число factual claims, потеря существенной информации,
latency/tokens/API cost. Так удаление почти всего ответа не становится улучшением.
Accuracy, source fidelity и полнота не взаимозаменяемы. Если fidelity растёт,
а правильность/полнота падает, результат описывается как trade-off.

Для A: матрица ошибок, flag precision/recall/F1, ложные тревоги и technical coverage
**относительно labels внешнего judge**; против опубликованных human labels —
отдельная таблица только при наличии такого набора. Не смешивать reference types.
Для B: paired разницы по вопросу; seeds/claims не независимые наблюдения.
Если даём bootstrap intervals, ресемплируем группы вопрос/связанные статьи,
сохраняя все варианты вместе; малый пилот не доказывает широкой надёжности.

## 7. Реальная следующая последовательность и бюджет

| Шаг | Действие | Результат |
|---|---|---|
| 1 | Подготовить отдельный judge CLI: вход без labels, рубрика, schema, анонимизация, логи, модель/snapshot, стоимость | Воспроизводимая оценка без истории чата |
| 2 | Dry-run: проверить входы, hashes, объём, лимиты; затем малый API pilot на существующих 26 случаях | Расхождения verifier/judge и измеренная цена |
| 3 | Разобрать dev-ошибки, зафиксировать rubric/prompt и обработку неопределённости | Понятно, какие замечания verifier пригодны для пробного исправления |
| 4 | Реализовать bounded revision B1/B2 и автоматическое выделение claims; проверить на dev | Сопоставимые ответы и полный учёт claims |
| 5 | Зафиксировать итоговые конфиги, roster, размер выборки, лимиты и judge; затем открыть резерв | Одна итоговая paired оценка, без подбора по результату |
| 6 | Свести метрики, стоимость, расхождения оценщиков и ограничения в отчёт | Вывод, соразмерный полученным данным |

Предлагаемый технический лимит первого judge-пилота — USD 5 **внутри** общего
проектного потолка USD 100. Это не оценка фактической цены и не отдельный бюджет.
До отправки считаем стоимость полного planned input и лимита output/reasoning
по актуальной цене выбранной модели; резервируем стоимость queued/in-flight
запросов и retries. Используем единый ledger, не расходуем остаток автоматически.
После малого измерения определяем объём основной серии и второй проверки.
Batch используем, если он поддерживается выбранным профилем и выгоден по срокам;
скидку не предполагаем без проверки. Ключи не сохраняем в repo, wiki или prompts.

Переход к пилоту B требует сохранённых технически валидных результатов A,
разобранных расхождений, приемлемых полезных/ложных флагов по обозначенному
внешнему reference и измеренных затрат. Инженерные проверки v1 (не отвергать
всё подряд, находить разные типы проблем) сохраняются; экспертная истинность
этим не подтверждается. Плохой результат — причина отладки/отрицательного вывода,
а не просьбы студенту подтвердить удобные labels. Разработку B можно вести
параллельно подготовке оценки; заявлять улучшение до измерения нельзя.

Нынешние 8 dev-вопросов, 26 claims и 8 резервных вопросов не стали большим
benchmark. Предложение v1 о новых 12 dev + 12 evaluation остаётся предложением,
не созданным split. Объём фиксируется по измеренной цене до открытия evaluation.
При расширении корпуса baseline прогоняется на таком же корпусе, как B1/B2.

## 8. Основания и границы

- [Ранний разговор, 16 сентября](../../../LLM%20Wiki/advanced-ict-project/raw/transcripts/turns/turn-42-cac9f098-1a94-40ba-bb3b-6e7bdeb53df2.md):
  пользователь передал совет преподавателя сравнивать результаты сильной моделью.
- [MT-Bench / LLM-as-a-judge](https://arxiv.org/abs/2306.05685): исследует модельную
  оценку и её position/verbosity/self-enhancement biases. Результаты о человеческих
  предпочтениях не доказывают точность научного source-support judge.
- [ALCE](https://aclanthology.org/2023.emnlp-main.398/): разделяет correctness и
  citation quality; наш протокол — адаптация, не воспроизведение его метрик.
- [SciFact](https://aclanthology.org/2020.emnlp-main.609/): готовые экспертные
  научные claims с evidence abstracts и rationales; потенциальная калибровка.
- [ARES](https://aclanthology.org/2024.naacl-long.20/): его статистическая
  корректировка использует human annotations. Мы не реализуем ARES/PPI и не
  приписываем нашему judge-only сравнению их гарантии.

Для отчёта: «Оценка с помощью фиксированного внешнего LLM judge, дополненная
эталонными ответами LitQA и проверками устойчивости; без новой экспертной
разметки наших ответов». Не писать «экспертно доказанная фактическая точность».
Viktor участвует в постановке эксперимента, понимании ошибок и интерпретации
результата. Массовая предметная разметка на него не возлагается.
