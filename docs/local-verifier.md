# Локальный verifier: observer v1

**Текущий результат 3 октября:** [B0/B1/B2 pilot завершён](../results/reports/2026-10-03-bounded-revision-pilot.md). Оба способа исправили выбранные ошибки, B2 дороже. Обнаружены смысловые ошибки extraction; сырые scores не пригодны для ранжирования. Следующий шаг — faithful extraction и whole-answer evaluation. API ledger $0,796048, 93 calls; holdout не использован.

Отдельная команда проверяет заранее подготовленные утверждения по полным исходным
цитируемым фрагментам. Она не меняет ответы, индекс, prompts или цикл PaperQA.
Это реализация первого этапа [протокола](claim-verifier-protocol-v1.md), не обучения
новой модели. Используется уже установленный Qwen3.8 27B Q4_K_M на UiA.

## Запуск из research/paperqa-reflect

```bash
.venv/bin/python -m paperqa_reflect.verifier plan
.venv/bin/python -m paperqa_reflect.verifier run
.venv/bin/python -m paperqa_reflect.verifier_report results/verifier/<run-id>
```

`plan` не делает сетевых вызовов. `run` использует только локальный Ollama на
127.0.0.1:11436, сверяет версию 0.35.0 и SHA-256 модели. На ноутбуке эта серверная
конфигурация не предполагает наличия 27B-модели; запускать inference в UiA.
Для одной технической проверки можно передать `--case-id cv-001`; этот запуск
остаётся отдельной попыткой и не подменяет полную серию. `--seed 43` создаёт новый
полный повтор, не перезаписывая seed42. Автоматических повторов ошибок нет.

Ollama должен быть запущен существующим `start-ollama-linux.sh` с версией0.35.0
и портом11436. Не запускать другие модели на этой GPU одновременно.

## Вход, выход и проверка

Inference читает только allowlist: `cases.jsonl`, `passages.jsonl`, а из manifest —
hashes для целостности. Claim, case ID и указанные полные тексты — единственные
данные в user message. Разметка/ключи/RCS/provenance не передаются модели.
Текст источников остаётся данными даже при наличии инструкций внутри.

Нативный `/api/chat` получает JSON schema, `think:false`, temperature0 и фиксированный
seed. Вердикт обязан иметь правильный case ID, допустимый label и точные цитаты из
доступных фрагментов. Offsets вычисляет программа. Существование цитаты подтверждает
её происхождение, **не смысловую правильность вердикта**. Это проверяется отдельно.

Timeout, невалидный JSON/schema, выдуманная цитата, неизвестный источник, лимит
вывода или обнаруженное усечение дают `not_checked`, без смыслового label.
Сохраняются request, raw response при его получении, verdict, error type/message,
время и token counters; status `completed` означает окончание серии, не успешную
проверку каждого случая. При прерывании остаются результаты завершённых случаев.

## Уточнение параметров до первого inference

Первоначальный подготовительный профиль предполагал context16384. Для реализации
v1 принят **32768 только в verifier**, с тем же max output1024. Причина: консервативный
byte-based контроль полного входа и возможность совместно проверять два длинных
исходных фрагмента без обрезки. Baseline остаётся на16384. Это изменение записано
до первого запроса. [Первая серия завершена](../results/reports/2026-10-03-verifier-first-run.md); независимая оценка качества остаётся впереди.

Предварительный budget = сумма UTF-8 bytes сообщений + длина model template +1024
резервных единиц; к нему прибавляется output budget. Это завышенная оценка для
закреплённого byte-level tokenizer, **не точный подсчёт токенов**. Слишком большой
вход не отправляется. После ответа проверяются фактические token counts и новые
строки серверного лога на признаки truncation; отсутствие/ротация лога делает
случай непроверенным. Стратегия рассчитана на закреплённый Qwen и последовательные
запросы; для других tokenizer/runtime нужна новая проверка, не слепой перенос.

## Результаты и независимая проверка

Каждый запуск получает новую папку `results/verifier/<UTC>-<id>`, snapshots
конфига, кода, prompt/schema, model metadata и hashes входа. Оценщик запускается
**отдельно после inference**. По умолчанию он сравнивает с assistant draft labels:
это agreement, не независимая accuracy. Natural/controlled таблицы разделены;
technical failures остаются в знаменателе agreement_all. Неопределённые метрики — null.

По [протоколу оценки v2](evaluation-judge-protocol-v2.md) внешний LLM judge
является планируемым основным оценщиком. Его labels не являются human gold,
для них нельзя ставить independently_adjudicated:true. [Judge CLI](external-judge.md) реализован, API pilot ожидает ключа. Обязательной разметки студентом нет. При наличии добровольного
предметного проверяющего можно дополнительно заполнить копию
`data/verification/claim-support-dev-v1/human-review.blank.jsonl`, опираясь на
`review-worksheet.md` и полные passages, до просмотра предсказаний. В каждой строке
нужны label/reviewer_id/rationale/evidence; спорные случаи оставлять unresolved и
сначала разбирать. Для финально согласованного файла можно явно проставить
`independently_adjudicated:true` и передать `--annotations <path>`; программа не
выдаёт простое наличие файла за выполненную независимую проверку.

Текущий прототип не извлекает claims автоматически и не исправляет ответ.
Результаты observer и внешний dev-аудит предусмотрены перед измеренным
пилотом bounded revision; обязательная человеческая разметка снята в v2.

API сверено по официальным источникам:
[Ollama chat](https://docs.ollama.com/api/chat),
[structured outputs](https://docs.ollama.com/capabilities/structured-outputs).
